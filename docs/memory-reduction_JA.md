# セッションのメモリは減らせるか（検討、2026-10-26）

ある質問と、既に分かっていることから導いた答えの記録。ここに書いたことは何も実装していない。
オーナーは FreeRDP のソースをじっくり読んでから手を付けたいので、このページは計画ではなくその出発点。
根拠にした測定は [code-notes_JA.md](code-notes_JA.md) の「メモリモデル」と
[KNOWN_ISSUES_JA.md](../KNOWN_ISSUES_JA.md)（「FreeRDP が使わない展開用バッファーを確保する」と heaptrack の内訳）にある。

## 質問

Windows クライアントで 3840×2160 のセッションを 6 本開くと、Iruka は約 7 GB になった（2026-10-26）。
メモリを圧縮する方法はないか。画素数を減らすのではなく圧縮率を上げる（JPEG の画質設定のように）とか、
捨てるフレームを増やすとか。それとも Iruka 全体が大きいから解決策はないのか。

## 短い答え

そのどちらでもメモリは減らない。ただし解決策がないわけでもない。メモリは「Iruka 全体」ではなく、
セッションごとの展開済み画素のバッファーにあり、そこには別の手がある。

## 圧縮率を上げても効かない理由

- RDP の画質の設定（RemoteFX / Progressive の画質、H.264 のビットレート）が変えるのは、ネットワークを
  流れるバイト数だけ。
- 画面を表示するには、クライアントは生の画素に展開しなければならない。1 画素 4 バイト、3840×2160 なら
  1 枚 32 MB で、画質がどうであっても同じ。
- セッションのメモリのほとんどはこの種のバッファーで、大きさはデスクトップで決まる。1920×1080 の
  セッション 1 本の heaptrack の内訳（Linux、2026-10-09）: FreeRDP の Planar デコーダー（2 組）約 71 MB、
  Progressive デコーダー約 42 MB、その他の FreeRDP のコーデック（ClearCodec、zgfx…）約 40 MB、
  描画用フレームバッファー約 8 MB、WebView の canvas 約 30〜45 MB、Iruka 自身のフレーム受け渡しはほぼ 0。
  どの行も画素数に比例する。
- H.264 / AVC444 にすれば通信量は減るが、デコーダーの分メモリはむしろ増える。

## フレームを多く捨てても効かない理由

- フレームを捨てて減るのは CPU と WebView へのコピーで、常駐メモリではない。バッファーはセッション
  開始時にデスクトップの大きさで確保され、その大きさのまま。
- Iruka はすでにフレームを捨てている。2026-10-25 の端から端までの流量制御が、セッションごとに
  送信中のフレームを 1 枚に保ち、残りは捨てる（[code-notes_JA.md](code-notes_JA.md) の流量制御の節）。

## 効きそうな手（どれも未着手）

1. **サムネイルで見ている間はリモートの解像度を下げる。** いちばん大きい。RDP は接続したまま
   リモートのデスクトップの大きさを変えられる（Display Control 仮想チャネル。FreeRDP の
   `/dynamic-resolution`）。一覧表示の間は 1280×720 で受け、拡大したら 3840×2160 に戻せば、
   展開用バッファーは約 1/9 になる。代償: 変更のたびにリモートのデスクトップがウィンドウを並べ直す。
   サーバーが大きさの変更に対応している必要がある。FreeRDP のバッファーが本当に縮む必要がある
   （2 を参照。FreeRDP の再確保の一部はメモリを返さない）。
2. **FreeRDP が確保して使わないバッファーをなくす。** 3840×2160 のセッション 1 本あたり約 150 MB。
   `gdi_ResetGraphics` が、使われないもう 1 組のコーデック用バッファーをデスクトップの大きさで作る
   （KNOWN_ISSUES_JA.md）。Windows では FreeRDP を vcpkg で自分たちでビルドしているので、パッチ
   （overlay port）を当てられる。Linux では Ubuntu のパッケージを使っているので、修正は上流に出すことになる。
3. **Windows が余分に使っているメモリの行き先を調べる。** 3840×2160 のセッション 1 本は、Linux で
   約 550 MB、Windows で約 1.2 GB。この 650 MB の差はまだ測っていない。疑わしいのは WebView2 側
   （32 MB のフレームのメッセージ、canvas、GPU のテクスチャ）。最初の一歩は、測定値を `iruka.exe` と
   `msedgewebview2.exe` の各プロセスに分けること。WebView が原因なら、サムネイルだけで見ている
   セッションのフレームを Rust で縮小してから送れば、そのメモリと、同じ日に見た 10 秒の固まりの
   背景にある転送コスト（開発ビルドで 32 MB のフレームが WebView に届くまで約 1 秒）の両方が減る。
4. **セッションを閉じた後に残るメモリ**（Linux の glibc の malloc アリーナ）: TODO_JA.md に記載済みで、
   オーナーの判断で保留中。

取りかかるときの順番の案: まず 3 を測る（手軽で、WebView と FreeRDP のどちらが大きな的かが決まる）。
その後、2 と 1 のために FreeRDP の gdi / RDPGFX のコードを読む。

## 余談: Microsoft のリモート デスクトップ クライアント

Microsoft 純正のクライアント（mstsc / Windows App）は、大きなセッションをたくさん開いてもずっと軽く
感じる。測ってはいないが、理由はおそらく作りの違い: DirectX で GPU のサーフェスに描き、H.264 を
ハードウェアでデコードできるので、展開した画面はプロセスのメモリではなくビデオメモリにある。
デコーダーと画面の間にブラウザーエンジンも挟まらない。Iruka はソフトウェアでシステムメモリに展開し
（FreeRDP の gdi）、各フレームを WebView の canvas にコピーするので、どの画素も少なくとも 2 回持っている。

### 回線が悪いとき

オーナーの観察: 遅延が多い回線では、Microsoft のクライアントは荒い JPEG のような画面を出して後から
鮮明にし、接続を保つ。その一部はクライアントではなくサーバーの働き:

- 荒い画面から鮮明になるのは RDPGFX の **Progressive** コーデック（RemoteFX Progressive）。サーバーは
  タイルごとにまず粗い版を送り、帯域に余裕ができたら細部を足す。**ネットワーク自動検出**でサーバーは
  往復時間と帯域を測り、画質とフレーム数を下げる。Iruka は FreeRDP にこの両方を指定している
  （`src-tauri/src/rdp/freerdp.rs` の `/gfx` と `/network:auto`）ので、接続先が Windows なら Iruka でも
  同じように画質が落ちるはず。まだ見ていない。
- Iruka にたぶん欠けているもの:
  - **UDP での送信。** Microsoft のクライアントは RDP を UDP で運べる（MS-RDPEUDP。Azure Virtual Desktop
    では RDP Shortpath）。UDP では失われたパケットが後続を止めない。FreeRDP のクライアントはこれを
    実装していないとされ、Iruka は TCP だけで動く。TCP は再送をすべて待つ。2026-10-25 に Wi-Fi の
    9 秒の停滞でセッションが切れたのはこのため（今は `/timeout:60000` と自動再接続）。
  - **H.264。** 次の節。

### Windows Server の H.264 と、Iruka のビルド

- Windows Server 2016 以降（エディションは問わず、Datacenter も、Azure VM でも）と Windows 10/11 は
  H.264/AVC で送る。既定では混合で、文字や静止部分は Progressive などのコーデック、動画のような部分
  だけを H.264 で送る。グループポリシー「リモート デスクトップ接続で H.264/AVC 444 グラフィックス
  モードを優先する」で画面全体が AVC444 になる。
- Azure VM の多くは GPU がないので、サーバーは H.264 を vCPU でソフトウェア圧縮する（動きが多いと
  重い）。GPU 付きの VM（NV シリーズ）はハードウェアで圧縮でき、別のポリシーで有効にする。
- サーバーが H.264 を使うのは、クライアントが展開できると申告したときだけ。Iruka の Windows 版は
  できない: vcpkg の FreeRDP 3.32.2 の `freerdp/config.h` では `WITH_GFX_H264`、`WITH_OPENH264`、
  `WITH_MEDIA_FOUNDATION`、ffmpeg がすべて未定義（2026-10-26 確認）。そのため Windows のサーバーは
  Progressive などのコーデックで送ってくる。有効にする方法: vcpkg で FreeRDP の `ffmpeg` 機能を足す
  （ビルドが長くなり DLL が増える）、または Windows 標準の Media Foundation のデコーダーを使うビルド
  （たぶん DLL は増えない。未確認）。Linux 版は Ubuntu の FreeRDP パッケージを使っており、おそらく
  ffmpeg 付きでビルドされているので、すでに H.264 を受けている可能性がある。未確認。

### H.264 で得られるもの、得られないもの

続けて出た質問は、ffmpeg（H.264）はメモリと引き換えに CPU を使うのか、というもの。メモリは減らない:

- **メモリは減らず、少し増える。** 展開結果は同じ 1 画素 4 バイトの画面で、gdi のフレームバッファーも
  WebView の canvas も残る。H.264 のデコーダーは参照用の画面を数枚持ち（3840×2160 の YUV 4:2:0 で
  1 枚 10 MB 強）、FreeRDP は Progressive などのコーデック用バッファーも従来どおり確保する。セッション
  あたり数十 MB 増えると見込まれる。AVC444 は内部で H.264 を 2 本流すので、さらに増える。
- **クライアントの CPU は展開の仕方による。** 4K の H.264 をソフトウェアで展開するのは重いが、今の
  Progressive もソフトウェアで展開しているので、どちらが重いかは画面の内容次第で、測る必要がある。
  ffmpeg は GPU でも展開できる（FreeRDP の `WITH_FFMPEG_HWACCEL`。Windows では D3D11 など、Linux では
  VA-API）。CPU の負担の大半がなくなる。それでも FreeRDP は gdi の画面を組み立てるために結果を通常の
  メモリに書き戻すので、節約できるのは CPU で、メモリではない（Microsoft のクライアントは展開した
  画面を GPU に置いたまま）。
- **サーバーの CPU は増える。** GPU のない VM は H.264 を vCPU で圧縮するので、激しい動きの負担は
  監視される側が払う。
- **監視用途では**、ほとんど動かない画面はどのコーデックでも送るデータが少ないので、H.264 の得は
  小さい。効くのは動画や画面全体が動き続ける場合で、回線が細いとき。2026-10-26 に 4K の画面全体を
  送り続けたセッションのような場合。

まとめると、H.264 で得られるのは帯域と、回線が悪いときの粘り強さで、代わりに CPU（と少しのメモリ）を
使う。メモリを減らす手は上に書いたもの: サムネイル時の低い解像度と、FreeRDP の使われないバッファー。
